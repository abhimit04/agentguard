# PostgreSQL write-path inventory

Updated 2026-09-30. Scope: runtime request handlers, background workers, and migration/bootstrap paths. This document distinguishes the telemetry tranche delivered here from the rest of roadmap milestone 1. SQLite local mode is outside the PostgreSQL audit guarantees.

## Telemetry paths covered by the transaction repository

Implementation: `repositories/telemetry.js`. Shared transaction-local audit writer: `repositories/governance.js::appendEventWithClient`.

- `POST /api/gateway/agents/:id/heartbeat` and `/events`: resolve the agent from PostgreSQL and authenticate the current agent credential. The URL, optional agent header, and supplied body identity must agree. Lock the agent row, recheck credentials, reserve the event receipt, update runtime state, and append non-heartbeat audit evidence within one transaction. Publish the cache only after commit. Invalid identity/authentication is rejected; database failure returns 503.
- `GET /api/gateway/agents/:id/status` and `/health`: read persisted state and credentials, so revocation and runtime state do not rely on stale process-cache values.
- `POST /api/gateway/events`: one company/agent identity per batch, with an explicit workspace header when IDs are ambiguous. Current agent/company credentials are checked in the transaction. The existing server-wide integration key remains a privileged credential; narrowing that onboarding/integration authority is a separate isolation task. All accepted events in a batch commit or roll back together.
- `POST /api/agent-events` and `/api/v1/events`: existing integration-key authorization followed by repository ingestion. PostgreSQL mode requires prior registration; inline metadata no longer implicitly creates an unknown agent. Supply company/workspace identifiers when a legacy agent ID is ambiguous. Legacy started/running/completed/failed names continue to drive runtime state.
- Managed runtime snapshots and connection-probe failures: `refreshManagedConnection` uses the current persisted agent. `updateRuntime` locks and rechecks the active URL and connection intent before committing state and audit/incident evidence. A stopped, archived, or rebound agent cannot be overwritten by an obsolete probe result. Database errors are not converted into runtime health failures.
- Idle/offline sweeps: `expireStates` reads PostgreSQL candidates, locks and reevaluates each agent, and persists only current transitions. These liveness changes do not create routine heartbeat audit noise. Failed database writes are reported instead of silently ignored.
- Connector/OTLP adapter forwarding: `connector/server.mjs` and `connector/company-gateway.mjs` forward to `/api/gateway/events`, so accepted downstream ingestion uses the same transaction. Connector-side response/retry behavior remains a separate verification item; this tranche does not certify durable buffering in the connector itself.

The transaction commits runtime state, receipt, audit event, and any telemetry incident/in-app alert together. External webhook delivery still follows commit and lacks a transactional outbox; it is not guaranteed across a crash in that interval.

## Idempotency, tenant identity, and migration contract

- `ag_telemetry_receipts` is keyed by workspace, company, agent, and caller-supplied event ID. Retries must reuse the same ID for the same event; a caller must not reuse it for different content. Concurrent retries and later process restarts do not double-count usage or duplicate audit events.
- Event IDs remain optional for compatibility. Requests without one receive atomic persistence but cannot promise duplicate suppression. Historical events before receipt activation are not automatically backfilled; do not replay historical traffic as if it already has receipts.
- Heartbeats receive retry receipts when identified but do not produce activity/audit events. Receipts are delivery metadata, not an alternate audit history.
- Workspace headers select an identity; they grant no authority. Credentials are verified against that workspace's agent or company, including under the row lock. Ambiguous identities fail instead of choosing a tenant.
- The new table is additive and created by the existing relational schema initialization. JSON backup and restore scripts now include it; older JSON snapshots need a fresh backup before the updated drill. The scheduled SQL backup format already captures database tables, but its restoration is still a separate roadmap gate.
- Rollback to older application code leaves the additive table intact but also loses the new transactional ingestion guarantees. Do not drop receipts as part of rollback.

## Remaining business writes — repository present, transaction proof still open

`test/write-boundary.test.js` now provides a static guard: runtime audit-event DML belongs only in the governance repository, and request handlers/repositories cannot directly write `agentguard_records`. `scripts/test-governed-execution-postgres.js` adds a database trigger after fixture/bootstrap initialization that rejects all compatibility-mirror inserts, updates, and deletes while its HTTP and restart workflow runs. These checks passed on 2026-09-30. They prove only the runtime paths exercised and source files included in the guard; they do not retire one-time initialization/import logic or migration scripts.

These paths must be addressed before calling milestone 1 complete or deleting compatibility data:

- Workspace membership create/role-update/delete now use transaction-backed repository operations that append chain-linked evidence atomically. Mutations share a workspace advisory lock so concurrent owner demotions/removals cannot both pass the last-owner check. The legacy membership import on the members endpoint also uses audited transactions. Disposable PostgreSQL API tests inject audit failure for create/import-sensitive mutations, role update and deletion, verify rollback, and then check a successful add/change/remove chain. `requestContext` still has a cache-based environment-bootstrap step; multi-instance bootstrap convergence, stale role caches between processes, and strict production membership-only authorization remain open.
- Company create, gateway credential rotation, and gateway provisioning now use `repositories/agents.js::saveCompanyWithAudit` in PostgreSQL mode. Creation and its audit event, or credential/name updates and their audit events, commit in one transaction with workspace-scoped lookup and stale-write protection. The integration test injects audit failures for both user-managed company creation/rotation and gateway provisioning create/rotation, checks rows and prior credential/name remain unchanged, then checks successful writes produce evidence. Gateway provisioning remains privileged by the platform integration key; least-privilege onboarding credentials and cross-instance name/ID allocation races need follow-up. SQLite keeps its local compatibility path.
- Workspace agent registration, manual edit/archive, bulk registration, gateway agent onboarding, agent credential rotation, and connection start/stop use transaction-backed repository writes in PostgreSQL. Every mutation and its hash-chained audit record commit together; bulk is all-or-nothing. Gateway onboarding can create the company and agent atomically, with separate evidence for both. Connection start first durably records the requested state and then probes; the resulting connected/error state and probe evidence are a separate transaction because the external runtime call cannot be enclosed in a database transaction. Cross-instance races for binding the same runtime URL and cache coherence remain open.
- Policy creation/update: PostgreSQL create/edit now uses `savePolicyWithAudit` to commit the policy row and its hash-chained audit event in one transaction. Edits lock and compare the previously loaded version, so concurrent stale edits conflict rather than overwrite newer values. The disposable-PostgreSQL test covers rollback on audit failure, create collision, version conflict, and exactly one audit record per successful version. SQLite retains its local path. Tool-permission behavior is unchanged by this tranche.
- `/api/guard/check`: PostgreSQL now locks and re-reads the agent and policy snapshot, evaluates the unchanged tool grant and policy/budget rules, then commits runtime activity, approval/action state, hash-chained decision evidence, and any incident/alert as one transaction. SQLite retains its existing implementation. Implicit registration/cache-only agent writes are not included in this transaction cutover.
- Reviewer approve/deny: PostgreSQL decision, governed-action state, and hash-chained audit evidence now commit together. Expiry is rechecked after locking the approval; a late decision becomes an atomic expiry with incident/alert evidence. Manual approval creation validates its agent from PostgreSQL and commits the approval, `approval.required` evidence, in-app reviewer alert, and webhook outbox item in one transaction. The outbox delivery contains an Approvals-page review URL and uses the existing signed webhook and idempotency mechanism. Reviewer authorization/tenant filtering still controls access to the page; the notification does not authorize or execute the action. The disposable PostgreSQL integration verifies audit-failure rollback leaves no orphan approval notification, and a successful manual approval creates exactly one alert and queued outbox item. Email/Slack adapters and expiry reminders are not included.
- Execution claim/completion: ledger update and audit append already share transactions. Full API identity, parameter binding, downstream uncertainty, and real workflow proof remain milestone 2 work.
- Approval expiry worker: approval, ledger, audit, incident and alert records share a transaction. The expiry alert carries the expired approval/action metadata and an atomic webhook outbox row, so the same alert reaches the signed webhook path as a request notification. The disposable PostgreSQL workflow directly expires a due approval through the worker and verifies alert/outbox persistence. This is not a reminder/escalation scheduler.
- Assessment create/update now reads the authoritative workspace agent/assessment in PostgreSQL and saves the assessment row plus its hash-chained audit event in one transaction. Per-agent advisory locking and update-time checking avoid duplicate first creates and stale overwrites. Immutable assessment revisions, versioned scoring, and scheduled reviews remain product work.
- Manual incident updates and alert acknowledgements now commit row state and audit evidence atomically; duplicate acknowledgements return conflict. Generic governance-signal creation commits its audit event, incident, and in-app alert together. Failure injection verifies both rollback and successful linked rows. Webhook alert delivery still stores its delivery result and delivery audit separately after the network call; move it behind a durable outbox before promising crash-safe external delivery. Continue auditing every fallback read for workspace filtering and stale cache behavior.
- Webhook delivery/retry: PostgreSQL has a durable `ag_alert_outbox` keyed by workspace/alert/channel. Explicit delivery requests enqueue before network I/O; a bounded worker also discovers open alerts missed by a crash between alert creation and dispatch. Approval creation inserts its in-app alert and webhook outbox item in the same transaction as the approval and audit row. Workers claim rows with `FOR UPDATE SKIP LOCKED` and a lease, so abandoned in-flight work is retried and concurrent instances do not claim the same live lease. Each attempt's delivery-history row, outbox transition, and hash-chained success/failure audit event commit together. Transient failures use bounded exponential retry; after five attempts work becomes `dead`. Requests use a stable `x-agentguard-idempotency-key`, but delivery is at-least-once: a receiver must honor that key to suppress the unavoidable duplicate if it accepted the request just before AgentGuard crashed. Approval webhook payloads identify the event and link to the signed-in Approvals page; the endpoint itself remains protected by workspace authorization. SQLite retains the older direct-send behavior. The disposable PostgreSQL workflow exercises outbox failure rollback, lease recovery, retries, completion, approval-notice rollback/persistence, and live signed webhook delivery.
- Evidence export: `GET /api/evidence/audit.ndjson` first appends the export-request event to the PostgreSQL audit chain, then streams the requested bounded segment as signed NDJSON. A disposable end-to-end PostgreSQL test verified authenticated download, Ed25519 manifest signature, exact-byte digest, event chain, offline verification, tamper rejection, and durable export audit evidence. Export artifact persistence and immutable external retention remain the caller's responsibility; signed checkpoints can be made offline, while restore-before-prune and the future transactional legal-hold gate are open.
- Audit legal holds: workspace-scoped create/release writes the hold row and hash-chained audit event in one PostgreSQL transaction. Owner/admin can create; only owner can release. An active hold is durable, but no production audit-pruning path exists yet. Any future prune transaction must recheck active holds under lock and require verified archive, restore, and independently retained checkpoint evidence. The disposable PostgreSQL test verifies rollback on injected audit failure, cross-workspace isolation, and recovery of active and released holds plus their audit chain from a JSON snapshot into a second scratch database. Scheduled SQL backup restoration with a post-schema hold remains to be exercised.
- Audit retention settings: owner/admin writes a workspace-scoped period and incremented version on `ag_workspaces` in the same transaction as `audit.retention.configured`. Stale versions are rejected. The read-only preview counts older audit events and active holds, and always returns cleanup disabled pending archive/restore proof; there is no deletion write path. The disposable PostgreSQL test verifies tenant isolation, rollback on injected audit failure, and recovery of settings from a JSON snapshot.
- Risk assessments: owner/admin writes update the current `ag_assessments` record, append an immutable `ag_assessment_revisions` row, and append `assessment.updated` to the hash chain in one PostgreSQL transaction. Each revision records its model, score, reviewer, rationale, evidence references, and review date. Stale head updates are rejected; an injected audit failure rolls back both the head and revision.
- Assessment-relevant agent edits use two transactional paths. Company, parent, risk tier, data class, or autonomy changes update the agent, mark the current assessment `review_required`, and append both audit records in one transaction. Tools, runtime URL, agent type, framework, model, or deployed version update the agent and append a bounded pending-change record plus `assessment.change_recorded` evidence without invalidating approval. Tool changes preserve added and removed names. Neither path alters immutable assessment revisions; saving a reviewer revision clears the pending batch.
- Assessment review scheduling: an approved assessment inside the configured advance window creates one `assessment.review_upcoming` audit event, in-app alert, and webhook outbox row per version in one transaction. It intentionally creates no incident. Once overdue, the existing `assessment.review_due` transaction creates evidence, incident, alert, and outbox delivery. Both paths deduplicate by workspace, assessment, and immutable version.

## Shared storage and audit hazards still open

`storage.js::writeStore` is cache-only in PostgreSQL mode. Normal runtime code no longer contains a compatibility writer and no longer creates or alters `agentguard_records`; fresh PostgreSQL installations seed the relational workspace/company rows directly. When relational workspace data is absent, startup performs a read-only presence check against an already existing compatibility table and fails closed if it or the legacy PostgreSQL blob/local SQLite/JSON files contain application data. This preserves an explicit migration escape hatch without making legacy storage part of normal operation. `npm run migrate:relational` handles only an existing compatibility-record table; PostgreSQL-blob and local-file importers remain to be built. Migration scripts and audit-chain repair scripts have explicit direct database writes; classify them separately and restrict them operationally before final table retirement.

The fail-closed decisions are covered by `test/startup-bootstrap.test.js`; both disposable PostgreSQL integration harnesses now seed relational fixture workspaces explicitly and pass their process-restart workflows without depending on developer-local files. The explicit compatibility-store migration command is `npm run migrate:relational` (after backup); it is intentionally not run automatically at application startup. No automatic importer exists yet for local SQLite/JSON or the old PostgreSQL JSON blob.

`scripts/inspect-local-cutover.js` compares local SQLite and JSON snapshots to each other and to PostgreSQL's relational tables; database reads are in a read-only transaction and payloads are never printed. The 2026-09-30 run found 18 SQLite agents vs 8 JSON agents (all shared agent IDs have payload differences), 9 approvals in each with every payload different, 414 SQLite events vs 45 JSON events (45 payload mismatches and 369 SQLite-only), and one JSON-only policy. PostgreSQL had 47 agents, 16 approvals, and 11,389 events; 8 SQLite event IDs were absent from PostgreSQL, while 406 shared events differed in payload. PostgreSQL had event hashes and sequence numbers for all 11,389 rows, whereas neither local snapshot had stored hash or sequence values. Treat all snapshots as conflicting until the event differences and source chronology are reconciled; counts alone do not authorize a merge or overwrite. Local-only audit events must not be inserted into the middle of the existing chain as if they were original chain members.

`scripts/inspect-postgres-cutover.js` is a read-only diagnostic for this migration boundary. The 2026-09-30 run against the local `.env` database found relational tables are the startup source and all required relational tables exist, but the mirror is not in parity: agents have 38 selected-payload mismatches, approvals have five relational-only rows and two payload mismatches, policies include a legacy-only row, and audit event keys differ in both directions. Membership comparison checks email, display name, subject, and role (timestamps/source metadata are intentionally excluded). This says the old mirror is stale, not which representation should overwrite the other. Do not run a reverse import or drop the table based on counts alone; first back up and reconcile against the authoritative relational rows and audit-chain verification.

Non-telemetry callers still use `event()` and its queued audit appends. Some calls are not awaited; `flushAudit()` currently waits on a catch-normalized chain. Those paths are not covered by the new acknowledgement guarantee. Finish their transaction conversion rather than claiming that flushing the old queue proves success.

Other instances may still have stale configuration/membership caches. Dashboard audit/state reads use repositories in several places, but not every decision does. Background connector discovery still begins from the process's connection inventory even though each probe result is revalidated against PostgreSQL. Fleet-wide discovery and cache refresh need multi-instance testing.

## Verification delivered

The audit verifier now scans in keyset pages with bounded per-page memory. Workspace-authorized `GET /api/audit/verify` offers resumable HMAC-signed cursors, and `GET /api/audit/events` offers fixed-ceiling keyset browsing; the Activity UI exposes both. `verifyAuditPage` now rejects cross-workspace rows as well as invalid predecessor links and hashes. The local PostgreSQL verifier passed for all 11,389 events in workspace `default` at the recorded check. Signed contiguous NDJSON export and its offline verifier passed `npm run test:audit-export-postgres`, an authenticated disposable-PostgreSQL HTTP workflow that checks signature, digest, chain, tampering, and export audit evidence. Offline verification supports trusted keyrings across key rotations while retaining single-key PEM compatibility. The same scratch-PostgreSQL workflow now verifies an archived copy, signed checkpoint, and linked continuation. The archive commands never prune database history. Independent immutable storage, tenant retention policies, legal holds, and restore-before-prune gating remain open.

Run `npm run test:telemetry-postgres`. It creates a uniquely named scratch database, applies the schema, starts an isolated HTTP server, and removes only that scratch database afterward. It uses local fixture credentials and never writes test data to the running application database.

Assertions cover:

- Atomic HTTP batch rollback on an injected audit failure, including runtime state, receipts, events, and the published process cache.
- Runtime-repository rollback when its audit write fails.
- Concurrent retries, durable receipt replay from a fresh Node process, and exactly one audit row for each accepted identified event.
- Two workspaces with colliding company and agent IDs, wrong-tenant agent/company credentials, URL/header/body conflicts, ambiguous identity rejection, credential revocation and archived-agent rejection.
- Per-agent events/heartbeat, batch ingestion, both legacy aliases, failed-task incidents, idle/offline persistence, and hash-chain validity.
- A database trigger prohibiting runtime writes to `agentguard_records`, so normal request paths cannot silently fall back to the compatibility mirror.

`node --test test/gateway.test.js` verifies existing status and heartbeat semantics. The managed HTTP probe itself is not exercised by the new integration script; its transaction callback and rollback are exercised. The expanded `scripts/test-governed-execution-postgres.js` passed on 2026-09-30; in addition to its approval/execution/restart flow, it verifies policy create/edit auditing, rollback when audit append fails, duplicate-create and stale-version conflicts, and audit counts. Full live connector, multi-instance configuration races, and broader write-path failure coverage remain explicit open gates. The scheduled SQL backup restore also passed as recorded in `ROADMAP.md`; staging/CI restore evidence is still pending.

Compatibility retirement is now in its read-only quarantine stage: runtime creation and mutation code has been removed, while startup may inspect an existing table only to prevent unsafe implicit bootstrap. Final retirement remains blocked on divergent-data reconciliation, a signed backup, successful hosted restore proof, and removal of the explicit migration/inspection dependency. No legacy data or existing tables have been removed.

Backup provenance: `scripts/postgres-backup-manifest.js` signs newly created SQL manifests when the independent backup signing key is configured. `scripts/restore-drill-postgres.js` verifies a present signature against the externally retained public key before restoring; unsigned historical manifests remain a documented compatibility exception. The backup writer must not control the trusted public-key location in production.

Ingestion safety: request parsing rejects bodies larger than `AGENTGUARD_MAX_BODY_BYTES` (default 1 MB), gateway batches reject more than 500 envelopes, and local rate buckets are keyed by route plus a hashed caller identity. A rejection is transport admission control and is not written to the audit chain; the process counter is operational telemetry. A shared limiter remains required for multiple instances.
