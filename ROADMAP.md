# AgentGuard enterprise delivery roadmap

Updated: 2026-09-30. Consolidates the original five-part reliability and governance roadmap with the additional repository, audit, recovery, deployment, and product requirements.

## Current status

- **Implemented with partial targeted PostgreSQL evidence, not release-verified:** telemetry transactional writes; approval-to-execution repository workflow; paged audit verification; workspace-bound keyset browsing; and Ed25519-signed NDJSON audit segments with an offline verifier. The passing targeted tests do not yet establish complete route coverage or production readiness.
- **Still a release blocker:** complete repository cutover, end-to-end governed execution/failure/restart proof, staging recovery automation, TLS/proxy deployment validation, tenant-aware rate-limit coverage tests, and operational failover/overload evidence.
- **Still planned product work:** reviewer reminders/escalation beyond expiry, evidence-based enforcement coverage, richer policy simulation, spending controls, immutable external archive storage, and restore-before-prune gates. Initial versioned risk assessments, signed offline checkpoints, workspace legal holds, and retention settings with a read-only candidate preview are implemented; audit pruning remains disabled. Approval requests and expiries create in-app alerts and durable webhook outbox entries in their state/audit transactions. Email/Slack adapters are not included.
- Tool permissions and tool naming remain unchanged at the user's request.

## External review reconciliation (2026-09-30)

The independent review is accepted with two factual corrections. AgentGuard already applies a process-local request limiter to gateway and integration routes, but it is not shared across instances, identities, or tenants and therefore does not satisfy the production abuse-control gate. Audit NDJSON exports and archive checkpoints use Ed25519 signatures, and SQL backup manifests now support Ed25519 signatures; the production gap is enforcing independent key retention and requiring signed manifests for every new backup.

Accepted priorities, in release order:

1. **Retire compatibility paths.** Freeze the current write inventory, reconcile divergent local/legacy data, implement any explicitly approved import, remove runtime/bootstrap dependencies, then delete compatibility code only after a backup and restore drill. Working decommission target: **2026-10-15, before client staging sign-off**. The date is a gate, not authorization to delete unresolved data.
2. **Prove staging recovery.** The first hosted run of `postgres-restore-drill.yml` succeeded on 2026-10-01 and retained its report as evidence. Exercise a protected production-like backup artifact in staging; local and synthetic CI success are not substitutes.
3. **Replace local throttling.** Add workspace-, company-, agent-, credential-, route-, and payload-aware limits using a shared store, bounded request bodies/batches, backpressure, and observable rejection metrics. Test multiple application instances and noisy-neighbour isolation.
4. **Separate backup trust.** Sign SQL backup manifests with a key unavailable to the backup writer, retain the public trust record outside the backup location, and verify the signature before every restore drill.
5. **Reduce reassessment fatigue.** Hard governance changes (`companyId`, `parentId`, `riskTier`, `dataClass`, `autonomy`) immediately require review. Operational changes (`tools`, `runtimeUrl`, `agentType`, `framework`, `model`, `version`) are accumulated as reviewed evidence without invalidating approval. Tool changes preserve added and removed names. Thresholds and policy/model dependency rules remain future work.

Progress (2026-09-30, compatibility quarantine): Normal PostgreSQL runtime code no longer creates, alters, or mutates `agentguard_records`; the dormant mirror writer has been removed, and fresh database seeding writes relational workspace/company rows directly. Startup retains only a read-only check for a pre-existing compatibility table so unresolved data causes a fail-closed migration message rather than silent loss. Explicit migration/inspection scripts remain until reconciliation and hosted recovery evidence authorize final table retirement.

Progress (2026-09-30, backup provenance): SQL backup manifests can now carry an Ed25519 signature using a separately configured private key and key ID. The restore drill verifies signed manifests against a public key kept outside the backup directory; unsigned historical manifests remain accepted only for migration compatibility. Production backup policy should require signed manifests before the hosted restore gate is called complete.

Progress (2026-10-01, ingestion safety): Gateway and integration request bodies are bounded by `AGENTGUARD_MAX_BODY_BYTES` and telemetry batches remain capped at 500 envelopes. PostgreSQL deployments now use an atomic, shared fixed-window limiter keyed by route and a hashed caller identity; rejected callers receive `Retry-After: 60`. Local development retains the bounded in-memory fallback. Tenant/company/agent-aware quotas and multi-instance noisy-neighbour tests remain required.

Progress (2026-10-01, multi-instance limiter proof): Telemetry limits now apply separately at workspace, company, and agent scopes; a batch is charged for every envelope rather than as a single request. `scripts/test-rate-limit-multi-instance-postgres.js` launches two AgentGuard processes against one scratch database, proves a single agent cannot evade its shared cap by switching instances, and verifies a second company retains its capacity. The GitHub restore workflow runs this check. Broader sustained-overload, queue-depth, and proxy-address tests remain open.

Progress (2026-10-01, bounded telemetry admission): PostgreSQL telemetry ingestion now acquires a short-lived shared database lease before transactional work begins. The lease pool is globally bounded across instances and expires after a crash; full capacity returns a retryable `503` before telemetry is committed. The multi-instance workflow verifies saturation and release. Sustained load profiling and queue-latency objectives remain open.

## Delivery objective

Prove one complete governed execution: an authenticated agent requests an action, policy evaluation requires approval, execution waits, an authorized reviewer approves, only the bound action receives an execution grant, and its outcome is durably audited. Demonstrate denial, expiry, duplicate delivery, database failure, and recovery after a real process restart.

The next implementation milestone is repository and audit correctness. TLS preparation can follow alongside recovery work, but cannot substitute for correctness. Every production release must pass the durability, tenant isolation, recovery, and deployment gates below.

Tool permissions and tool naming are on hold at the user's request. This roadmap does not authorize further changes to those controls.

## Milestone 1 — Complete repository writes and durable audit acknowledgements

Priority: P0. Active repository write tranche.

- Progress (2026-09-30): the telemetry tranche is implemented in `repositories/telemetry.js`. PostgreSQL `/api/guard/check` now evaluates a locked agent/policy snapshot and commits runtime state, approval/action changes, audit evidence, and resulting incident/alert together. Reviewer approve/deny and manual approval creation commit approval state plus hash-chained evidence atomically; expiry is rechecked under lock. Policy create/edit uses optimistic version checking and atomic evidence. Manual/bulk agent registration, gateway onboarding, edit/archive, agent credential rotation, and connection start/stop now commit their PostgreSQL state and audit evidence atomically. For connection start, the request is durably recorded first; then an external runtime probe occurs and its result is recorded separately. Company creation and company gateway-credential rotation (workspace and gateway provisioning APIs) commit with hash-chained evidence in one transaction and reject stale updates. Workspace membership add/role-update/remove and legacy import append evidence in the same transaction; owner-role changes serialize within a workspace. Assessment create/update, incident updates, and alert acknowledgement now commit with their audit evidence atomically. Generic governance signals write their audit event, incident, and in-app alert in one transaction. A PostgreSQL webhook outbox persists work before network I/O, leases claims across instances, recovers abandoned attempts, retries transient failure with bounded backoff, and atomically stores each attempt with hash-chained result evidence. It is at-least-once; receiver-side idempotency is required to suppress a duplicate after the receiver accepted a request but AgentGuard crashed before recording success. Approval requests and expiries create reviewer alerts and outbox items in their state/audit transaction; the disposable integration proves failure rollback, persistence, worker expiry, and signed HTTP delivery/retry. A new source-level guard centralizes runtime audit DML in the governance repository, and the disposable workflow passes with compatibility-table writes denied. Remaining risks include legacy bootstrap/migration, cross-instance URL-binding and company ID allocation races, environment-bootstrap convergence, and general cache coherence. See [the write-path inventory](WRITE_PATH_INVENTORY.md); Milestone 1 remains open until all listed paths and retirement gates pass.

1. Inventory every mutating route and background worker: registry/onboarding, credentials, membership bootstrap, company gateway, per-agent heartbeat/events, batch gateway ingestion, legacy events, managed polling, idle/offline transitions, policies, approvals, assessments, incidents, alert delivery, and evidence export.
2. Record each path's authenticated identity, workspace/company scope, repository operation, transaction boundary, audit event, retry key, failure response, and integration test. Follow the connector's HTTP destinations as well as server handlers.
3. Move remaining PostgreSQL mutations behind repositories. Make database state authoritative; invalidate or refresh caches after commits. Eliminate cached snapshots as decision authority for approvals, credentials, agent state, and memberships across instances.
4. Commit related state changes, audit events, and delivery-outbox records together. Await the actual transaction result before returning success. Audit persistence failure must fail the operation, not be hidden by a queue flush or become an unhandled background rejection.
5. Persist telemetry deduplication with a unique workspace/company/agent/event identity. Duplicate deliveries must not double-count usage or audit events, including after restarts. Heartbeats update liveness without reintroducing routine heartbeat activity logs.
6. Bind tenant identity to validated credentials or session membership. Reject conflicting caller-supplied identifiers. Explicitly document whether a workspace is the isolation boundary and how company scopes nest within it; company names alone are not an isolation mechanism.
7. Remove implicit production fallback/bootstrap into legacy records after migration validation. Keep migration/import tooling explicit. SQLite remains a separately selected local mode, not a PostgreSQL failure fallback.

Acceptance:

- Disposable PostgreSQL tests exercise every inventoried mutation and verify persistence after cache reset and real process restart.
- For every accepted auditable event, verify its expected ID and valid hash in `ag_audit_events`. Assert no corresponding writes to compatibility event storage; run normal paths with legacy-table access denied. Ordinary business tables may retain references, not a second authoritative event history.
- Inject audit/database failure and confirm there is no successful acknowledgement or partially committed business operation. Retrying the same accepted event remains idempotent.
- Test two companies/workspaces, colliding external identifiers, stale credentials, and two application instances. One tenant cannot read, mutate, export, or verify another's data.
- Retire compatibility code only after backup, restore proof, migration reconciliation, and staging smoke tests pass. Archive legacy data with a documented rollback boundary before separately authorizing physical deletion.

## Milestone 6 — Ingestion limits and overload behavior
